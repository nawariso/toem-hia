# ADR-010: MediaStore and Local Filesystem Development Adapter

Status: Proposed (Requirement 003, pending independent review)

## Context

Requirement 003 lets a signed-in user photograph a Hia and attach the photo to one of their own DRAFT encounters. Photos are private personal data: they can show people, places, and times, and camera files may carry EXIF location. The project must keep the mandatory external runtime cost at **$0/month** during core development (ADR-004) and must not depend on any SaaS (ADR-005). There is no deployed environment yet, so there is no production storage to target.

## Decision

- **`MediaStore` port** (`internal/application`): `Stage(ctx, reader, limit)` streams bytes to a staging area and returns a handle with size and SHA-256; the handle can be `Open`ed for inspection, `Commit`ted under a key, or `Discard`ed. `Open(key)` and `Delete(key)` serve reads and cleanup. The application layer never sees a path.
- **Local filesystem adapter** (`internal/infrastructure/media/localmedia`): `MEDIA_MODE=local` stores bytes under `MEDIA_LOCAL_ROOT` (`photos/<uuid>.jpg|png`, staging in `.staging/`, directories created `0700`). Staged files left by a crash are removed at startup. Commit is a same-volume rename that refuses to overwrite.
- **Metadata** lives in PostgreSQL `encounter_media` (migration `000003`): kind, status, content type, byte size, width, height, SHA-256, storage key, timestamps. Check constraints mirror the domain limits; `UNIQUE(storage_key)` and `UNIQUE(encounter_id, sha256)`; an update trigger makes content fields immutable; `ON DELETE RESTRICT` protects encounters that have photos.
- **Storage keys** are generated by the server (`photos/<uuid>.<ext>`), validated against that exact shape by the domain, the database, and the adapter before use, and never returned by the API.
- **Upload flow**: authorize (owner, `ACTIVE`, DRAFT) → stage (15 MiB cap) → inspect (magic-byte sniff, declared type must match, header dimensions bounded, full decode) → commit file → attach row under the encounter's `FOR UPDATE` row lock (re-checks DRAFT, the 5-photo limit, and duplicates) → on failure or duplicate delete the just-published file.
- **`MEDIA_MODE` is required** (`local` | `disabled`) with no default. `disabled` answers `503 MEDIA_UNAVAILABLE`.

## Security boundary

- The API is the only reader and writer of `MEDIA_LOCAL_ROOT`. Nothing serves that directory directly; bytes are streamed by `GET /v1/media/{id}/content` only after the caller is shown to own the encounter (another user's photo is `404`, not `403`). Responses use `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff`, and a sandbox CSP.
- Response DTOs are allowlists: no storage key, path, device URI, EXIF, or location. Logs record request ID, IDs, and status only.
- The client never supplies metadata; width, height, size, hash, and type are measured by the server from the bytes.
- Decompression bombs: dimensions come from `DecodeConfig` on the header and are bounded (12000 px per side, 50 MP) **before** the full decode; the body is capped by `http.MaxBytesReader` before any read.

## Production fail-closed rule

`APP_ENV=production` with `MEDIA_MODE=local` is a fatal startup error (config load), in the same way as `AUTH_MODE=local`. A production deployment must choose `disabled` until a production `MediaStore` adapter exists. There is no fallback from one mode to another.

## Alternatives considered

- **Cloud object storage now (S3, R2, GCS, Supabase Storage):** needs an account, credentials, and either spend or free-tier limits before any deployment exists; violates the $0/SaaS-free core-development constraint and adds secrets to local setup.
- **Bytes in PostgreSQL (`bytea`/large objects):** simple and transactional, but grows the system-of-record database and its backups with blobs and makes a later move to object storage a data migration rather than an adapter swap.
- **Client-supplied metadata or presigned direct uploads:** shifts validation to the device; not acceptable for untrusted input and not possible without an object store.
- **Multipart upload:** workable, but a raw body with an exact `Content-Type` is simpler to bound and stream and needs no envelope parsing. Kept provisionally.

## Why cloud object storage is deferred

There is no deployed API, no production user, and no pilot yet. The port isolates the choice, so selecting a provider (and its region, lifecycle, encryption, and cost) can be made with real requirements at Integration & Pilot Hardening without touching domain, application, or HTTP code.

## Consequences

- File and row are two systems. Publish-then-attach means a crash between the two can leave an unreferenced file (never a row without a file). Duplicates and attach failures delete the published file immediately; crash-orphans are not yet swept (technical debt).
- Local data is tied to one machine: deleting `MEDIA_LOCAL_ROOT` without resetting the database leaves rows whose content returns `404`.
- File permissions on Windows are not POSIX modes; the local adapter is a development tool, not a hardened store.

## Future replacement path

1. Implement `MediaStore` for the chosen object store (stage to a temporary object or local temp file, commit by copy/put under the same key shape, delete, open as a stream).
2. Add `MEDIA_MODE=<provider>` with its own required configuration and a startup check; keep `local` refused in production.
3. Copy existing objects key-for-key; keys are opaque and portable, so no metadata rewrite is needed.
4. Add an orphan sweeper that compares stored keys with `encounter_media.storage_key`.
